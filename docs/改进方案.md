# dsh-tool-gate 改进方案（v0.5）

> 目标版本：v0.4.0 → v0.5.0
> 依据：源码通读（17 个 lib 文件 / 3,886 行）+ 宿主 API 核对（cordis 0.2.x、dsh-tools 0.2.1-rc.5、dsh-system-prompt）+ 本机运行时实测（GUI :49920，插件已启用）
> 本文档回应三个问题：① 设置页两套列表合并；② 对第三方插件是否硬编码；③ 最不稳定与最慢的位置。

---

## 0. 结论摘要

| # | 问题 | 结论 |
|---|---|---|
| 1 | 列表合并 | **合并正确且必要**。`discovery.js` 的规则是「一个包 = 一个家族」，`family.packages` 虽声明为数组但实测每个家族恰好一个包 —— 1:1 关系下两张表本来就是一张。合并后行内嵌披露开关，披露总开关随 `enabled` 联动出现。 |
| 2 | 第三方硬编码 | **归属机制通用，但有三层硬编码会把第三方插件挡在门外**。最致命的是 `prompt-attribution.js` 的 33 条静态快照（新装第三方插件注入的提示词永远认不出），其次是 `keep-tools.js` 的 48 个常驻工具名（导致「工具常驻 ⇒ 无家族 ⇒ 提示词不可披露」），第三是 `callerPackage()` 读 `ctx.fiber.name`（拿的是本插件自己的 fiber，不是调用方）。**根因已定位并验证了正确通道**，详见 §2.3。 |
| 3 | 性能与稳定性 | **头号热点是一个自激循环**：本插件自己注册的网关工具名没有归属，每次签名计算都把它们交给全盘磁盘扫描，扫描永远认不出它们 → 下次还要再扫。实测 **320–408 ms/次**，去掉网关名后同一数据集 **0.1–0.5 ms/次**（差 700 倍）。冷/热路径都在每次工具调用上跑 ≥2 次。另有两个可独立验证的正确性 bug（自我归属污染、`dispose()` 恢复被静默跳过）。 |

### 已确认的五项决策

| # | 决策点 | 选择 |
|---|---|---|
| 1 | 合并后的行语义 | **一行 = 一个家族**，行内嵌提示词披露开关 |
| 2 | 常驻工具插件的提示词 | **不允许披露**，保持灰显并说明原因 |
| 3 | 与宿主 `deferLoading` 的关系 | **只保留 gateway**，`deferLoading` 仅作对照实验 |
| 4 | 归属层重构力度 | **carrier ctx 为唯一权威**，栈回溯降级并标注置信度，磁盘扫描默认关闭 |
| 5 | 配置兼容 | **允许破坏性变更**，`schemaVersion: 2` + 自动迁移 |

## 1. 列表合并

### 1.1 为什么两张表本来是一张

`lib/discovery.js:148` 的派生循环决定了每个包最多产出一个家族：

```js
for (const [toolName, pkg] of Object.entries(owners ?? {})) {
  ...
  let row = byPackage.get(pkg);      // 一个包 → 一行
  if (row === undefined) { row = { pkg, tools: [] }; byPackage.set(pkg, row); }
  row.tools.push(toolName);
}
for (const pkg of [...byPackage.keys()].sort()) {
  const id = uniqueId(familyIdOf(pkg), taken);
  families[id] = makeFamily(id, pkg, options);   // 一个包 → 一个家族
}
```

`makeFamily`（`discovery.js:96`）里 `packages: [pkg]` 恒为单元素数组。而 `promptPlugins`（`config.js`）的 key 正是包名。两条链路的主键相同，只是被拆成了两个 UI 段。

唯一会让一个家族对应多个包的是用户手写 override（`families[id].packages`，`discovery.js:230`）或 `mcp_servers` 家族（`packages: []`，靠 `prefixes: ["mcp__"]` 收口）。合并后的行必须能表达这两种情况 —— 见 §1.3。

### 1.2 现状的四个具体缺陷

`lib/client.js` 当前分四段（总开关 / 家族折叠 / 提示词披露 / 行为细节）：

1. **同一实体出现两次**。13 个家族 + 42 个插件行，用户需要在两处对照「这个包属于哪个家族」。
2. **披露总开关在家族未折叠时也可点**（`client.js:318-321`，disabled 只判 `busy || !ready || !enabled`）。此时打开它什么也不会发生 —— `shouldBlank()`（`prompt-scan.js:143-160`）要求 `isCollapsedFamily(family)` 为真。
3. **逐插件行的禁用原因是文本推断出来的，不是数据**（`client.js:334-344`）：`blocked` 只来自 `disclosureAvailable`，hint 再用 `families.length === 0` 猜是「未归属」还是「未收起」。`disclosureAvailable` 本身又是在 `inventory()` 里用 `isCollapsedFamily(family) && !isRequired && !NEVER_BLANK` 现算的（`prompt-scan.js:379`）—— 三处逻辑各说各话。
4. **实测 42 行里只有 4 行可用**，其余 38 行灰显。用户看到的大量灰色开关里，真正「有提示词但不可披露」的有 6 个（`dsh-tool-goal` 1056 字符、`dsh-client-ui-deliverables` 2608、`dsh-tool-workflow` 650、`dsh-tool-terminal` 616、`dsh-mcp-resources` 314、`dsh-subagent` 108），它们的共同原因是工具全在 `CORE_TOOLS` 里 → 无家族 → 永不可披露。这正是决策 2 要明确处理的边界。

### 1.3 合并后的数据模型

**桥接层（`lib/bridge.js`）改为一次请求返回合并后的行**，`plugins` 数组不再独立存在，改为挂在家族行上：

```jsonc
{
  "families": [
    {
      "id": "blender_plugin",
      "label": "Blender",
      "gateway": "blender_plugin",
      "builtin": false,
      "enabled": true,            // 收起开关（原 families 段）
      "count": 15,
      "tokens": 8415,
      "packages": ["dsh-blender-plugin"],
      "promptDisclosure": {       // ← 新增：原 plugins 段并入此处
        "available": true,        // 三态：ready / no-prose / requires-collapse
        "reason": "ready",
        "chars": 0,
        "names": [],
        "required": false,
        "enabled": false
      }
    }
  ],
  "ungrouped": [                   // ← 新增：无家族的包，只读
    {
      "package": "@deepseek-ai/dsh-tool-goal",
      "reason": "resident",        // resident | no-tools | unowned
      "toolCount": 3,
      "chars": 1056,
      "names": ["tool:goal"],
      "enabled": null              // 永远是 null：不可开关
    }
  ]
}
```

**关键点**：`promptDisclosure.reason` 取代 `client.js` 里的文本猜测。枚举值与判定来源：

| reason | 判定（`prompt-scan.js`） | UI |
|---|---|---|
| `ready` | 有 prose、家族已收起、无 required 项 | 可开关，hint 说明随哪个家族披露 |
| `requires-collapse` | 有 prose、家族存在但 `enabled === false` | 灰显，「先收起该家族」 |
| `resident` | 有 prose、但包的所有工具都在常驻表 → 无家族 | 灰显，「工具常驻，提示词不参与披露」 |
| `no-prose` | 归属成功但当前没有注入任何段落 | 灰显，「未向提示词注入内容」 |
| `required-only` | 有 prose 但全部命中 `NEVER_BLANK` / `required` | 灰显，「含必需上下文，永不摘除」 |
| `unowned` | `packageOf(name)` 返回 undefined | 灰显，「无法归属到包」 |

`ungrouped` 数组承接决策 2：常驻工具包的提示词行仍然**可见**（用户能知道这个插件注入了 1056 字符），但**不可操作**，且必须给出原因 —— 不是静默消失。

### 1.4 客户端结构

```
[启用工具网关]                        ← 总开关，disabled: busy||!ready
  ├ (enabled 时) [自动成族]
  ├ (enabled 时) [内置插件也折叠]
  └ (enabled 时) [插件提示词随 list 披露]   ← 移到此处，随 enabled 联动
──────────────────────────────────────
家族折叠与提示词披露          已收起 9 个家族 · 约省 31,948 tok
  ▸ Blender         15 个工具 ≈8.4k tok  [内置?]    [收起 ✓]
                                 └ 提示词随 list 披露 ✓   ← 行内第二行
  ▸ GitHub          14 个工具 ≈2.7k tok             [收起 ✓]
                                 └ 提示词无注入
  ▸ MCP 管理        25 个工具 ≈5.4k tok             [收起 ✓]
                                 └ 提示词 3248 字符 ✓
──────────────────────────────────────
未参与折叠（工具常驻）                        只读
  · @deepseek-ai/dsh-tool-goal      3 个工具 · 提示词 1056 字符
                                    工具常驻，提示词不参与披露
  · @deepseek-ai/dsh-client-ui-deliverables  提示词 2608 字符
──────────────────────────────────────
行为细节
  [listDetail] [staticNotice] [interceptDirectCalls] [guardFallback] [concurrencyDelegate] [freeze]
  [未知归属策略: expose/collapse]
  [全部家族收起] [全部家族常驻]
```

**互锁规则**（一处定义，三处复用）：

- `promptDisclosure` 总开关：`disabled = busy || !ready || !enabled`，且 `!enabled` 时**不渲染**（不是灰显）。这就是用户要的「开启网关折叠之后，才显示开启提示词披露的开关」。
- 家族行的披露子开关：`disabled = busy || !ready || !enabled || !promptDisclosure || row.promptDisclosure.reason !== "ready"`。
- 批量按钮「全部插件可披露」改为「全部 ready 家族开启披露」，只对 `reason === "ready"` 的行写 `promptPlugins`。

### 1.5 配置结构变更（`schemaVersion: 2`）

披露开关从独立字典并入家族 override：

```yaml
# v1（旧）
promptPlugins:
  dsh-free-search: { enabled: true }
# v2（新）
families:
  free_search:
    enabled: true
    promptDisclosure: true
```

`config.js` 的 `families` 条目加一个字段：

```js
promptDisclosure: z.boolean().default(false)
  .description("是否把该家族的插件提示词从上下文摘掉，改为在 action=list 时随成员定义披露。仅在该家族已收起、且总开关打开时生效。"),
```

**迁移**（`lib/migrate.js`，新文件）：`apply` 早期读 `schemaVersion`，若为 1 且 `promptPlugins` 非空，则对每个 `{pkg, enabled:true}` 找到 `family.packages.includes(pkg)` 的家族，写 `families[id].promptDisclosure = true`，然后清空 `promptPlugins` 并把 `schemaVersion` 置 2。迁移必须幂等，并且**在家族表第一次解析之后**才能做（需要 `families` 才知道 id）。无法映射的包（无家族）记录一条 `logger.warn` 后丢弃 —— 反正 v1 下它们也从未生效（`shouldBlank` 要求 `family !== undefined`）。

`promptPlugins` 字段保留一个版本（标记 `.hidden().deprecated()` 语义上等价），只读、不参与判定，避免老 profile 直接报校验错。

## 2. 通用性审计：对第三方插件是否硬编码

### 2.1 审计结论

**归属与成族机制是通用的**：`discovery.js` 不列举任何插件，装一个新插件下次装配就自动成族；`owner.js` 的 L2 静态表也只在「注册表实际认识这个工具名」时才生效（`owner.js:320`），所以不会为未安装的插件凭空造网关。这部分的设计是干净的。

**但有三层硬编码会实际挡住第三方插件**，按危害排序：

| 序 | 位置 | 内容 | 对第三方的影响 | 危害 |
|---|---|---|---|---|
| **A** | `lib/prompt-attribution.js` | 33 条精确规则 + 1 条 `mcp:*` 前缀 | 第三方插件注入的提示词段**永远认不出** → 永远不可披露 | **高**（功能直接缺失） |
| **B** | `lib/keep-tools.js` | CORE 36 + OPS 7 + CONTEXT 5 | 常驻工具不产生家族 → 其提示词不可披露 | **高**（设计级缺口） |
| **C** | `lib/prompt-scan.js:255` `callerPackage()` | 读 `ctx.fiber?.name` | 拿的是**本插件自己的** fiber 名，不是调用方 → live 归属恒失败，只能靠 A 的静态快照兜底 | **高**（A 的失效放大器） |
| D | `lib/family-labels.js` | `BY_PACKAGE` 9 条 + `BY_ID` 1 条 | 只影响展示名，不影响归属 | ~~低（可接受）~~ → **高**（见下） |
| E | `lib/builtin-attribution.js` | 141 条 tool→package | 只对第一方工具；第三方走 live/扫描 | 低（可接受） |
| F | `lib/prompt-scan.js:48` `NEVER_BLANK` | 7 条段名 | 硬编码的「永不清空」名单，第三方无法自声明 | 中（见 §2.4） |
| G | 前缀判定三处不一致 | `discovery.js:50` `FIRST_PARTY_PREFIXES`、`index.js:66` `THIRD_PARTY_PREFIXES`、`bridge.js:124` 内联 `!pkg.startsWith("@deepseek-ai/")` | 影响「内置/第三方」标签与 `builtinFamilies` 开关 | 中（`@dsh-ops/dsh-ops` 在 bridge 算第三方、在 packages() 算内置） |

**D 项已升级为「高」**，理由见《[改进方案-网关描述与提示词分层](改进方案-网关描述与提示词分层.md)》§1.1：
它不只是「展示名难看」。表里没有的包会拿家族 id 当描述，而**每个网关的描述都要进每一轮
请求的前缀**——12 个网关各 351 B 的同一段使用说明就是 4212 B，占全部网关描述文本的 85%。
新装的第三方插件既拿不到名字，也拿不到描述，还得替它付这 351 B。该文档已改成
「描述从宿主 `pluginPackages` 读、本表只留短名兜底」，并把这笔字节账一并拆掉（v0.7 已落地）。

### 2.2 硬编码 A：提示词快照（首要问题）

`prompt-scan.js` 的归属是三层：

```
L1  live：包装 systemPrompt.section/context（prompt-scan.js:227-249）
L2  快照：PROMPT_ATTRIBUTION（prompt-attribution.js）
L3  兜底：mcp:<server> 前缀（prompt-scan.js:120-123）
```

L2 的注释（`prompt-attribution.js:6-7`）说明了它存在的理由：

> *"`systemPrompt.section()` / `.context()` are called during a plugin's `apply`, i.e. before dsh-tool-gate mounts (it is the last bundle in the profile). Wrapping the service only observes registrations that happen afterwards, so the already-registered names need a static table."*

这个理由**只对「本插件挂载前已注册」的段名成立，且这是可以消除的**：`adoptRegistered()`（`prompt-scan.js:211`）本来就会遍历 `layers` 里所有已注册条目 —— 它读得到名字和文本，只是读不到归属。

所以问题不是「快照无法避免」，而是「**快照是唯一的归属来源，而它不可能覆盖第三方**」。修完 C 之后，快照可以降级为「仅用于挂载前已注册的段的保底」，且必须能标注置信度。

### 2.3 硬编码 C：`callerPackage()` 用错了上下文 —— 已找到正确通道

当前实现：

```js
// prompt-scan.js:255-263
const callerPackage = () => {
  try {
    const fiber = ctx.fiber?.name;     // ← ctx 是【本插件】的 ctx
    if (typeof fiber === "string" && fiber !== "" && fiber !== "root") return fiber;
  } catch { /* fall through */ }
  return undefined;
};
```

`ctx` 是 `apply(ctx, config)` 收到的本插件上下文，`ctx.fiber.name` 是**本插件**的 fiber 名。所以 L1 永远返回 `"dsh-tool-gate"` 或 `undefined`。实测证据：`/describe` 的 plugins 列表里 `dsh-tool-gate` 自己一行 `chars=1923`，`names` 包含 `context:file-reference`、`tool:edit`、`tool:read`、`tool:subagent_fork` —— 全是别的插件的段。

**正确通道**：`cordis-plugin-loader` 给每个 Entry 建的 ctx 上挂着 entry 对象（`cordis-plugin-loader/lib/index.js:312`）：

```js
static key = Symbol.for("cordis.entry");
constructor(loader) {
  this.ctx = loader.ctx.extend({ [Entry.key]: this });
  ...
}
```

而 cordis 的 `Service` 在方法调用时，`this` 是绑定到**调用方**上下文的 traceable proxy（`cordis/lib/index.js:122-155` 的 `createTraceable`，`applyTraceable` 用 `value[symbols.invoke].apply(proxy, args)`），所以服务方法内部读 `this.ctx` 得到的是**调用方**的 ctx。

**已用最小复现验证**（`_probe_entry3.mjs`）：

```
[tool:A] entry="@acme/plugin-a" chain=["@acme/plugin-a", ...] 
[tool:B] entry="@acme/plugin-b" chain=["@acme/plugin-b", ...]
[tool:root] entry=undefined          ← root 注册，正确返回 undefined
```

**并且验证了「包装后的方法仍能拿到调用方」**（`_probe_wrap.mjs`，完全复刻 `prompt-scan.js` 的 patch 方式）：

```
patched: tool:A -> callerPkg="@acme/plugin-a"
patched: tool:B -> callerPkg="@acme/plugin-b"
patched: tool:root -> callerPkg=undefined
```

同时验证了 `tools.register` 同一条通道可用（`_probe_owner.mjs`）：

```
register(alpha_one) callerPkg="@acme/tool-alpha"
register(beta_one)  callerPkg="@acme/tool-beta"     ← 经过两层 extend 仍正确
```

**修法**（`lib/ownership-channel.js`，新文件，供 `owner.js` 与 `prompt-scan.js` 共用）：

```js
const ENTRY_KEY = Symbol.for("cordis.entry");

/**
 * Package that registered something on `ctx`, or undefined at root.
 * The loader puts its Entry on every plugin context under a well-known symbol;
 * reading it here is exact (no stack walking, no disk, no snapshot).
 */
export function packageOfContext(ctx) {
  let cursor = ctx;
  for (let depth = 0; depth < 8 && cursor !== null && cursor !== undefined; depth += 1) {
    try {
      const name = cursor[ENTRY_KEY]?.options?.name;
      if (typeof name === "string" && name !== "") return name;
    } catch { /* a hostile proxy: keep walking */ }
    cursor = Object.getPrototypeOf(cursor);
  }
  return undefined;
}
```

调用点改为 `const owner = packageOfContext(this?.ctx)`（`this` 是服务方法的 receiver，即调用方 ctx）。这一处修改让 L1 从「恒失败」变成「对任何插件——包括第三方——都精确命中」。

**为什么必须同时改 `owner.js`**：`owner.js:254` 的 `internal/get` 监听器签名是 `(carrier, property, _error, next)`，第 2 参数 `carrier` **就是发起解析的那个 ctx**（`cordis/lib/index.js:681`：`ctx.events.waterfall("internal/get", ctx, prop, error, ...)`）。当前代码丢弃了它。改为用 `packageOfContext(carrier)` 可以得到工具注册的**精确包名**，这直接消掉 §3 里的磁盘扫描需求。

### 2.4 硬编码 B：常驻工具表导致的「提示词不可披露」

`keep-tools.js` 的 48 个名字是快照，本身不是错误 —— 常驻集本质上是策略选择。真正的问题是它**同时决定了「有没有家族」**，而家族又是披露的前提（`prompt-scan.js:157-158`）：

```js
if (family === undefined || !isCollapsedFamily(family)) return false;
```

于是「工具常驻 ⇒ 无家族 ⇒ 提示词永不可披露」是结构性的，不是配置错误。

**按决策 2 处理**：不自救。这些包的提示词行进入 `ungrouped`，`reason: "resident"`，灰显并写明原因。这样用户在界面上能看到账（「这个插件注入 1056 字符，因为工具常驻所以不参与披露」），但不会误以为开关坏了。

**顺带的收益**：`keep-tools.js` 可以从「硬编码名单」降级为「默认值 + 运行时可覆盖」。新增 `config.residentTools: string[]`（默认空）与 `config.residentUnlessOptional: boolean`（默认 `true`：一个包的工具若全是常驻，该包不成族）。第三方插件若要让自己常驻，现在有配置入口，不必改插件源码。

### 2.5 硬编码 F：`NEVER_BLANK` 与 `required` 的自声明

`NEVER_BLANK`（`prompt-scan.js:48-56`）是 7 个段名，`required: true` 来自静态快照的 2 条（`team:identity`、`working-directory:current`）。这两个机制表达的是「这段提示词不可摘」，属于**注册方**的知识，不该由本插件硬编码猜测。

**修法**：支持注册方自声明。`adopt()` 已经替换了 `entry.text` provider，可以在包装对象上识别一个约定字段：

```js
// 注册方（任何插件）在 section/context 上标注即可，不需要改本插件
ctx.systemPrompt.section({ name: "team:identity", text: ..., mutable: false });
```

`shouldBlank()` 优先读 `entry.mutable === false`，其次读快照的 `required`，最后读 `NEVER_BLANK`。`NEVER_BLANK` 保留但降级为「对第一方已知段的兼容兜底」，并在注释里标明它是过渡措施。

### 2.6 硬编码 G：三处前缀判定合并

三处各自为政：

- `discovery.js:50`：`FIRST_PARTY_PREFIXES = ["@deepseek-ai/", "@dsh-ops/"]`
- `index.js:66`：`THIRD_PARTY_PREFIXES = ["@deepseek-ai/", "@dsh-ops/"]`（语义上是 first-party，命名是反的）
- `bridge.js:124`：内联 `!pkg.startsWith("@deepseek-ai/")` ← **不一致**

合并到 `discovery.js` 的单一导出：

```js
/** Package-name prefixes owned by the harness itself. Presentation only. */
export const HARNESS_PREFIXES = ["@deepseek-ai/", "@dsh-ops/"];
export const isFirstParty = (pkg) => HARNESS_PREFIXES.some((p) => pkg.startsWith(p));
```

`index.js` 与 `bridge.js` 删掉本地副本，统一 `import { isFirstParty }`。这样 `@dsh-ops/dsh-ops` 在三处都是「内置」。

### 2.7 修完之后的通用性判定

修完后，对一个**素未谋面**的第三方插件 `@acme/dsh-tool-widget`：

| 环节 | v0.4 现状 | v0.5 之后 |
|---|---|---|
| 工具归属 | live 包装（`register`）→ 有效 | `internal/get` carrier → 精确 |

### 第 1 名：`registered()` 的磁盘扫描 —— 一个自激循环

#### 证据

`owner.js:332-343`：

```js
const unplaced = new Set();
for (const name of candidates) {
  const owner = ownerOf(name);
  if (owner === undefined || owner === UNKNOWN) unplaced.add(name);
}
if (unplaced.size > 0) {
  for (const [name, pkg] of Object.entries(scanForOwners(unplaced, logger))) {
    scanned.set(name, pkg);
  }
}
```

`candidates` 来自 `known`，而 `known` 是 `knownNames()` —— 它遍历 `ctx.tools.schemas(...)`，**因此包含本插件自己注册的网关工具名**。

网关名（`blender_plugin`、`github`、`free_search`…）永远没有归属：它们不是任何插件 package 注册的工具，是网关。`scanForOwners` 在磁盘上永远找不到它们，所以 `scanned` 里永远没有它们的条目，`unplaced` 每次都非空，**每次调用都重扫全盘**。

#### 实测（`_probe_real3.mjs` / `_probe_real2.mjs`，同一 131 个真实工具名）

```
包含 13 个网关名（153 个名字）：
  registered() #1: 408.1 ms   placed 142/153
  registered() #2: 335.2 ms   placed 142/153
  registered() #3: 326.1 ms   placed 142/153
  registered() #4: 335.3 ms   placed 142/153
  registered() #5: 320.7 ms   placed 142/153

去掉网关名（141 个名字）：
  registered() #1: 0.4 ms     placed 141/141
  registered() #2: 0.1 ms     placed 141/141
  registered() #3: 0.1 ms     placed 141/141
  ...  unplaced: 0
```

**同一份磁盘、同一份缓存，差别只在于 11 个无法归属的网关名 → 700 倍差距。** 这 11 个是：`agent blender_plugin free_search fs fs_search github hindsight_coding_agents image_gen mcp_servers schedule session_query`。

`scanForOwners` 本身在 `_bench_scan.mjs` 里冷 323 ms / 热 247 / 232 ms；`tool-scan.js:67` 的 `cache` 只缓存「包的文件清单」，每次仍要 `statSync` + `readFileSync` 全部候选文件（`tool-scan.js:174`）。

#### 精度同样是坏的

`_probe_unplaced.mjs` 对 131 个真实名字跑一遍：放置 96 个，未放置 35 个 —— 而那 35 个里，`tool:goal`、`tool:workflow`、`tool:pty`、`context:file-reference` 等**是提示词段名，不是工具名**，扫描对它们毫无意义。此前对 48 个核心工具名的测试里，扫描只认出 1 个，且认错了：`web_search → dsh-free-search`（静态表说是 `@deepseek-ai/dsh-tool-web`）。原因是正则 `NAME_IN_SOURCE`（`tool-scan.js:47`）匹配 `name: "literal"`，谁先撞上算谁的。

#### 优化方案（三层，按优先级）

**① 网关名不进候选集（1 行，收益最大）**

```js
// owner.js registered(known)
registered(known) {
  const candidates = new Set([...live.keys(), ...preexisting]);
  if (known !== undefined) {
    for (const name of Object.keys(BUILTIN_ATTRIBUTION)) if (known.has(name)) candidates.add(name);
    for (const name of known) {
      if (isOwnGateway(name)) continue;      // ← 新增
      candidates.add(name);
    }
  }
  ...
}
```

`isOwnGateway` 由 `index.js` 注入（它知道 `gatewayNames`），或更稳妥地在 `knownNames()` 里就不收集网关名。**这一条单独就能把 320 ms 变回 0.1 ms。**

**② `internal/get` 的 carrier ctx 替代栈回溯与磁盘扫描（根因）**

```js
// owner.js:254
const offGet = ctx.on("internal/get", (carrier, property, _error, next) => {
  if (property !== "tools") return next();
  const tools = next();
  learnPreexisting(tools);
  record(tools, packageOfContext(carrier));   // ← carrier 就是注册方的 ctx
  return tools;
});
```

配合 §2.3 的 `packageOfContext`，绝大多数常驻工具的归属可以在**零 IO** 下确定。

**③ 磁盘扫描默认关闭，改为显式诊断**

```js
diskScan: z.union([z.const("off"), z.const("on-demand")]).default("off").volatile()
  .description("归属兜底：是否允许读取 profile 的 bundle 源码来推断工具归属。默认关闭——它每次约 250ms，且对压缩后的 bundle 精度很低。仅在排查「某个插件没有成族」时临时打开。"),
```

打开时也**只扫一次并永久缓存**（当前 `scanned` 是 per-name 缓存，但输入集变了就重扫）。加一个 `scanVersion`：扫描成功的结果按 `(profileDir, mtime of package.json)` 失效，而不是每次调用。

**预期收益**：热路径从 320–408 ms/次 → <1 ms/次，且每次工具调用跑 2 次（`guard.js:60` 与 `guard.js:88` 各读一次 `runtime.config()`），实际节省约 **0.6–0.8 s/次工具调用**。

### 第 2 名：`callerPackage()` 恒失效（正确性）

已在 §2.3 完整论证。这里补充它对**稳定性**的影响：因为 L1 恒失效，`learned` Map 几乎永远为空，`inventory()`（`prompt-scan.js:381`）的第三个数据源失效，整个披露功能**只能依赖静态快照**。装任何新插件 → 提示词不可披露，而 UI 不会报错，只是灰显 —— 这是最难被用户归因的失败模式。

### 第 3 名：`dispose()` 的恢复被静默跳过（稳定性 / 泄漏）

`prompt-scan.js:244-247`：

```js
restores.push(() => {
  if (service[method] === wrapper) service[method] = original;
});
```

`service` 是 `ctx.get("systemPrompt")` 返回的 **traceable proxy**，不是服务实例本身。在 proxy 上赋值会落到 shadow 上，读取回来永远不等于写入的 wrapper。

**已用最小复现确认**（`_probe_wrap3.mjs`）：

```
read back through proxy === wrapper ? false
read direct from real === wrapper ? true
RESTORE SILENTLY SKIPPED -> patch leaks past dispose()
```

后果：插件被禁用或重载后，旧的 `section`/`context` 包装**留在原处**，其闭包捕获着已 dispose 的 `config`/`withheld`。若该包装的 `shouldBlank` 读到失效引用，可能出现「提示词被清空但没有任何地方能恢复」的状态 —— 这是本插件最危险的一种失败。

**修法**：在服务实例本体上打补丁。cordis 给 traceable proxy 提供了原始对象符号（`cordis/lib/index.js:38`：`original: Symbol.for("cordis.original")`）：

```js
const ORIGINAL = Symbol.for("cordis.original");

/**
 * The real service instance behind a traceable proxy.
 * Patching the proxy writes to a shadow that the next read cannot see, which is
 * why restore-by-identity silently fails; patching the original is observable
 * by every caller and restorable.
 */
const realService = (service) => service?.[ORIGINAL] ?? service;
```

**已验证**（`_probe_original.mjs`）：

```
real[ORIG] === real ?          false | typeof: undefined     ← 原始实例上没有这个键
proxy[ORIG] === real ?         true                          ← 从 proxy 反向取出真实实例
real.section === wrapper ?     true                          ← 在真实实例上打补丁可被读到
RESTORE OK                                                   ← 身份比对恢复成功
```

在 `realService(service)` 上打补丁，`restores` 的 `target[method] === wrapper` 即可正确成立。另外把恢复改成**无条件还原**并记录一条 debug 日志，避免「静默跳过」这类失败再次隐形。

> **精度说明**：proxy 上的赋值确实会落到真实实例上（`_probe_wrap2.mjs`：打补丁后 `real.section === wrapper` 为 `true`），所以**功能上包装是生效的** —— 出问题的只有「读回来比对身份」这一步，因为每次读 `proxy.method` 都会拿到新的 shadow 包装。因此该 bug 的表现是**资源泄漏 + dispose 后旧包装仍在记录**，而不是归属失效。`owner.js:206-212` 的 `record(target)` 用完全相同的手法（`target.register = wrapper` + 身份比对恢复），有同一个泄漏问题，修法相同。

### 第 4 名：`bridge.js` `describe()` 64–66 ms

#### 证据

5 次采样：`0.066 / 0.066 / 0.065 / 0.065 / 0.064 s`，响应 13,623 bytes。

三个叠加的开销：

1. `runtime.membersOf(family.id, scope)` 对**每个家族各调一次** `ctx.tools.schemas(scope)`（`index.js:243`），13 个家族 = 13 次全量 deep-clone（`dsh-tools/lib/index.js:3119`：`.map(d => this.schemaOf(d, true))`，每次都 `snapshotJsonValue(parameters)`）。
2. `disclosure.inventory()` → `measure()`（`prompt-scan.js:290-315`）**逐条调用 provider 函数**求文本长度。
3. `runtime.packages()`（`index.js:304`）内部再调 `refreshFamilies()` → 又一次 `signatureOf()` → 又一次 `knownNames()` → 又一次全量 `schemas()`。

#### 修法

```js
// bridge.js describe()
const scope = agent ?? runtime.primaryAgent?.();
const all = ctx.tools.schemas(scope);                 // ← 一次
const byFamily = new Map();
for (const schema of all) {
  const id = runtime.familyOf(schema.name);
  if (id !== undefined) (byFamily.get(id) ?? byFamily.set(id, []).get(id)).push(schema);
}
```

- `membersOf` 改为接受「已取好的 schema 数组」的重载，避免重复 deep-clone：**13 次 → 1 次**。
- `measure()` 的字符数改为**按段名缓存**，仅在 `system-prompt/change` 事件后失效（`dsh-system-prompt` 每次注册/销毁都 `onChange()`）。设置页读的是静态规模，不需要每次重新求值 provider。
- `describe()` 开头显式 `runtime.config()` 一次并复用返回值，避免 `packages()` 内部的第二次 `refreshFamilies()`。

**预期**：64 ms → 5–8 ms。

### 第 5 名：`knownNames()` 每轮全量 `schemas()` deep-clone

`index.js:154-172` 对 `undefined` 和**每个 agent** 各调一次 `schemas()`。每轮 `handleAssemble` 首行 `refreshFamilies()` → `signatureOf()` → `knownNames()`。

实测（`_bench_hotpath.mjs`）：58 个工具、每工具 ~600 B 参数时，`schemas()` 全量 deep-clone **0.204 ms/call**。多 agent 会话（每轮可能有 3–5 个 agent 在册）时是 0.6–1.0 ms/轮。

**修法**：签名不需要 schema 内容，只需要**名字集合**。

```js
// dsh-tools 的 view(scope).knownNames 是 Set<string>，无 deep-clone
const knownNames = () => {
  const names = new Set();
  const collect = (scope) => {
    try {
      for (const name of ctx.tools.view(scope)?.knownNames ?? []) names.add(name);
    } catch { /* scope not resolvable */ }
  };
  collect(undefined);
  try { for (const agent of ctx.get("agents")?.list?.() ?? []) collect(agent); } catch {}
  return names;
};
```

`view()` 会重建三个 Map（`dsh-tools/lib/index.js:3055-3090`），但**不做 deep-clone**，实测路径的 0.204 ms 主要来自 `snapshotJsonValue`。同时 `signatureOf` 可以只 join 排序后的名字，不再 `JSON.stringify` 整个对象数组。

**预期**：0.6–1.0 ms/轮 → 0.05–0.1 ms/轮。

### 第 6 名：`syncGateways()` 的整批重建

`index.js:369-395`：签名变化时 `disposeGateways()` + `registerGateways()` 全量重建。家族表变化时（装插件、改开关）这会**替换 wire 上的全部网关定义**，即使只有一个家族变了。因为 `freeze` 已经让 wire 稳定，这条不是每轮开销，但会造成「改一个开关 → 全部网关重建 → 一次前缀重写」。

**修法**：改为差量同步。

```js
const syncGateways = (enabled) => {
  const want = enabled
    ? new Map(Object.values(families).filter(f => f.enabled !== false).map(f => [f.id, gatewayNameFor(f.id)]))
    : new Map();
  for (const [id, dispose] of mounted) {
    if (!want.has(id)) { dispose(); mounted.delete(id); }
  }
  for (const [id, name] of want) {
    if (mounted.has(id)) continue;
    mounted.set(id, ctx.tools.register(createGateway({ family: families[id], name, runtime })));
  }
};
```

未变家族的定义对象保持同一个引用，wire 字节不变。

### 第 7 名：`isConcurrencySafe` 缺 agent 作用域

`gateways.js:70`：

```js
const definition = runtime.ctx.tools?.get?.(args.tool);   // ← 无 scope
```

不带 scope 的 `get` 只看全局层（`dsh-tools/lib/index.js:3091`）。若成员工具是**在某 agent 作用域内注册**的（`dsh-tool-schedule`、`dsh-subagent` 就这么做），这里返回 `undefined` → 一律判为不安全 → 串行执行。功能上安全，但 `concurrencyDelegate` 对这些家族永久失效，属于静默降级。

**修法**：`execute` 拿得到 `exec.agent`，但 `isConcurrencySafe(args)` 签名里没有。两个选择：

- (a) 改为 `runtime.ctx.tools.get(args.tool, runtime.primaryAgent())` —— 简单，可用；
- (b) 若宿主给 `isConcurrencySafe(args, exec)` 传 exec（需核对），用它更准。

先按 (a) 修，并在注释里记录这个近似。

### 第 8 名：空家族 `agent` / `fs_search`

`/describe` 实测 13 个家族，两个 `count: 0`：

```
agent      count=0  packages=["@deepseek-ai/dsh-agent"]
fs_search  count=0  packages=["@deepseek-ai/dsh-tool-fs-search"]
```

根因：`@deepseek-ai/dsh-agent` **不注册任何工具**（702 行里只有 `agents.register(agent)` 这类非工具注册），`builtin-attribution.js` 里也没有它的条目 → 家族来自 `ownerFromStack()` 的栈回溯误归属（工具注册调用栈穿过了 `dsh-agent` 的 lib）。

`fs_search` 的成员 `glob`/`grep` 在 `prompt-attribution.js` 里被归给 `@deepseek-ai/dsh-tool-fs-search`，但工具名本身不在 `CORE_TOOLS` 里，理论上应该成族 —— 实测 `count=0`，说明 `deriveFamilies` 的 `RESIDENT` 过滤与 `membersOf` 的 visibility 两条路径不一致。

**修法**：修完 §2.3 之后，栈回溯层降级 → `dsh-agent` 不再被误判为 owner，`agent` 家族自然消失。同时**加一条不变量测试**：

```js
// test/run.mjs
assert.equal(families.filter(f => membersOf(f.id).length === 0).length, 0,
  "a derived family must have members — an empty family means a misattributed owner");
```

并让 `describe()` 对空家族返回 `hidden: true`，UI 不渲染（而不是显示一个「已收起 0 个工具」的行）。

**顺带清理**：profile `cordis.patch.yml:301-319` 里那条 `families: { agent: { enabled: true } }` 是为压空家族手写的 override，修完后应删除。

## 5. 风险与回滚

| 风险 | 概率 | 缓解 |
|---|---|---|
| `packageOfContext` 在某些打包形态下拿不到 entry（容器/预编译） | 中 | 保留 `BUILTIN_ATTRIBUTION` 作为 L2；`diskScan: "on-demand"` 作为手动兜底；CLI 里输出 `ownerConfidence`（`live-carrier` / `static` / `scanned` / `unknown`） |
| v1 → v2 迁移破坏用户现网配置 | 中 | 迁移前写 `.bak`；迁移幂等；迁移失败的包记 warn 而不中断；profile 里 4 个已启用插件路径纳入测试用例 |
| 合并列表后信息密度过高（42 → 13+6 行） | 低 | `ungrouped` 段默认折叠；家族行 meta 用 `title` 承载长名单 |
| 差量 `syncGateways` 引入网关残留 | 低 | `test/run.mjs` 加断言：`mounted` 的 key 集合 === 期望家族集合 |
| 去掉扫描后某些第三方工具不再成族 | 低 | `diskScan` 可临时打开；`ungrouped` 会显示 `reason: "unowned"`，用户可见而非静默 |

**回滚**：每个阶段一个 commit；`schemaVersion` 单向递增，回滚 v0.4 代码后配置会被读成 v2 但 v0.4 不校验 `schemaVersion`（它只写不读），因此回滚安全 —— 需在阶段 2 验收时显式验证这一点。
