# dsh-tool-gate 修复方案：空网关与家族标签（v0.7）

> 目标版本：0.7.0 → 0.8.0
> 依据：插件源码逐行复核（`lib/` 全部 20 个文件）+ 宿主 API 逐行核对（`@deepseek-ai/dsh-tools`、`@deepseek-ai/dsh-scope`、`@deepseek-ai/dsh-app-boot`）+ 本机 profile `desktop` 现场实测（两轮：`http://127.0.0.1:49593` 与 `http://127.0.0.1:50258`，均为 13 个家族，两个问题的现象逐格一致）+ `dsh-ops` 的掩蔽实现。
> 本文档只回答两个现场问题，**先出方案，不动代码**：
> 1. 为什么 Hindsight 显示成 `网关 · 记忆`，而不是 `网关 · Hindsight`；
> 2. 为什么 wire 上多出一个空网关 `网关 · 文件搜索工具`。
> 与既有文档的关系：`docs/改进方案-网关描述与提示词分层.md`（0.7.0 已落地）解决了「描述从哪来」，本文档处理它留下的两个判定错误——**label 的语义**与**空家族的判定集合**。0.7.0 的结论不被推翻，只是它把 label 的取值链写成了「表 > 宿主标题」，而表里混进了能力词。

## 0. 结论摘要

| # | 现场现象 | 根因（已定位到行） | 结论 |
|---|---|---|---|
| A | `hindsight` 家族显示 `网关 · 记忆：…` | `lib/family-labels.js:116` 的取值链是 `byPackage?.label ?? byId?.label ?? meta?.title ?? humanizeLabel(id)`——**静态表压过宿主标题**；表里 `:62-66` 那一行把品牌名写成了能力词 `记忆` | 不是缓存。改一行表 + 反转取值链优先级。宿主本身给不出 `Hindsight`，理由见 §1.4，所以**表是第一责任方**，不是「宿主没给」 |
| B | wire 上有一个 0 成员的 `fs_search` 网关 | `lib/index.js:528-543` 的 `emptyFamilyIds()` 用 `knownNames()`（`:194-218`，含 **scope-less 全局视图**，且 `knownNames` 按宿主定义**不受 restriction 过滤**）判「非空」→ 注册网关；而页面 `hidden`（`lib/bridge.js:167`）与 `membersOf`（`lib/dispatch.js:48-64`）用 `schemas(agent)`（只含 `visible`）→ 0 成员。**同一个家族被两套名字集合判定** | 不是缓存。把「判空」改成「各会话 scope 的 **visible** 并集，且优先组装中的 agent」；`knownNames()` 继续只用于归属推导 |

### 0.1 自查：三处「像缓存」的地方，逐个排除

用户的第一直觉是缓存，这个怀疑是合理的——现场确实有三层会让人误以为「改了没生效」。逐个查过：

| 层 | 是不是缓存 | 证据 |
|---|---|---|
| HTTP 响应 / 设置页 | 否 | `lib/bridge.js:49-58` 的 `send()` 每次带 `cache-control: no-store`；`lib/client.js` 全文无 `localStorage` / `sessionStorage` / 模块级缓存 |
| 家族表 / 网关注册 | 是「按签名复用」，但标签根本不来自这里 | `lib/index.js:278-288` 的 `refreshFamilies` 只在签名（`live.families` / `builtinFamilies` / `autoFamilies` / `residentTools` / owners）变化时重建；`lib/gateways.js:157-159` 的 `signatureOf` 只在 `[id,label,description,selfExplaining]` 变化时重注册。**改源码文件不会触发签名变化**——但这只解释「你手改源码后本会话不生效」，不解释 label 为什么是「记忆」：那个字符串来自编译进模块的静态表，重启进程也不会变 |
| 冻结的 wire surface | 是，而且是最容易误判的一层 | `lib/state.js:84-91` 的 `adopt()` 一旦设置 `frozen` 就不再重算（除非 `freeze:false`，见 `lib/config.js:93` 默认 `true`）；`lib/index.js:670-689` 只在该 state 的 `frozen === undefined` 时重建；`lib/index.js:700-711` 的 notice 也只建一次。**因此「改了源码/配置，本会话没变」是设计内的行为，不是 bug**，但它是问题 B 的一半成因（§2.6） |

结论：A 是语义错误（表里写错了词），B 是判定集合错误（两套名字集合），两者都与缓存无关；而「像缓存」的观感由第三层（冻结面）负责解释。

## 1. 问题 A：为什么是「网关 · 记忆」

### 1.1 现场

```
$ curl -s http://127.0.0.1:<GUI 端口>/api/dsh-tool-gate/describe | jq '.value.families[] | select(.id=="hindsight_coding_agents")'
{ "id": "hindsight_coding_agents", "label": "记忆", "count": 8,
  "descriptionSource": "manifest",
  "description": "Reflect-only Hindsight long-term memory for coding agents (harness-pluggable: opencode, …), with automatic background…" }
```

wire 上对应工具的 description：

```
网关 · 记忆：Reflect-only Hindsight long-term memory for coding agents (harness-pluggable: opencode, …), with automatic background…
```

同一时刻其余 12 行：`Blender`、`Computer Use Win`、`搜索`、`文件读写工具`、`文件搜索工具`、`GitHub`、`图像`、`MCP 管理`、`日程`、`会话检索`、`Tavily`、`视频`。

### 1.2 根因：静态表压过宿主标题

`lib/family-labels.js:113-120`：

```js
export function familyLabelHints(id, pkg, meta) {
  const byPackage = pkg === undefined ? undefined : BY_PACKAGE[pkg];
  const byId = BY_ID[id];
  const label = byPackage?.label ?? byId?.label ?? meta?.title ?? humanizeLabel(id);   // ← :116
  const description = byPackage?.description ?? byId?.description ?? "";
  const gateway = byPackage?.gateway ?? byId?.gateway;
  return gateway === undefined ? { label, description } : { label, description, gateway };
}
```

`meta?.title` 排在第三位，所以只要表里有行，宿主标题永远看不到。hindsight 那行在 `lib/family-labels.js:62-66`：

```js
"@vectorize-io/hindsight-coding-agents": {
  label: "记忆",
  description: "Repository memory: knowledge pages, capture, recall",
  gateway: "hindsight",
},
```

`"记忆"` 就是全部原因。这个字符串在模块加载时编译进内存，重启进程也不会变成别的——它从来不是一个「旧值」。

### 1.3 更深一层：表里混了两种语义

把 9 行表（外加两个无表行、靠 `humanizeLabel` 的家族）按语义分类，问题立刻清楚：

| 包 | 表的 label | 语义 | 该不该翻译 |
|---|---|---|---|
| `dsh-blender-plugin` | `Blender` | **品牌**（产品名） | 不译 ✅ |
| `@perrylink/dsh-github` | `GitHub` | **品牌** | 不译 ✅ |
| `dsh-free-search` | `搜索` | **能力** | 译 ✅ |
| `dsh-image-gen` | `图像` | **能力** | 译 ✅ |
| `dsh-video-storyboard` | `视频` | **能力** | 译 ✅ |
| `dsh-mcp-connector` | `MCP 管理` | **能力** | 译 ✅ |
| `@deepseek-ai/dsh-tool-session-query` | `会话检索` | **能力** | 译 ✅ |
| `@deepseek-ai/dsh-tool-schedule` | `日程` | **能力** | 译 ✅ |
| **`@vectorize-io/hindsight-coding-agents`** | **`记忆`** | **品牌被写成能力** | **不该译 ❌** |
| （无表行）`dsh-computer-use-win` | `Computer Use Win` | **品牌/能力混用**，走 `humanizeLabel` | 不译 ✅ |
| （无表行）`@moguiyu/dsh-tavily` | `Tavily` | **品牌**，走 `humanizeLabel` | 不译 ✅ |

Hindsight 是 Vectorize 的产品名（该包 `package.json` 的描述与 README 都写 "backed by [Hindsight](https://vectorize.io/hindsight)"，`plugin.json` 的 MCP server 名就叫 `hindsight`）。它是唯一一个**品牌被写成能力词**的条目——这正是为什么用户只在它身上觉得别扭：其它中文短名读起来是「这是干什么的」，只有 `记忆` 读起来像「这是干什么的」而不是「这是谁」。

顺带一个反证：`docs/设计蓝图.md:355` 当初的设计表写的就是 `| \`hindsight\` | Hindsight | 8 |`。**实现与设计意图已经偏离**，不是设计如此。

### 1.4 为什么宿主也给不出 `Hindsight`

如果只是「表压过宿主」，反转优先级就够了。但实测表明反转今天不会改变任何一行——因为宿主对这个包确实说不出一个可用的名字：

1. **没有 `locale/` 目录**：`readPluginMeta` 的 title 回退到 `manifest.name`，即完整包名 `@vectorize-io/hindsight-coding-agents`（`dsh-app-boot/lib/index.js:2216` 起的 `readPluginMeta`，`title = localizedText("title", dictionaries, fallbackText(manifest?.name), specifier)`）。
2. **`lib/plugin-meta.js:228-234` 会主动丢弃「等于包名」的标题**：

```js
const title = rawTitle !== undefined && rawTitle !== specifier && rawTitle !== barePackageName(specifier)
  ? rawTitle
  : undefined;
```

所以它走到表里的 `记忆`。**这个丢弃是对的**（否则 `GitHub` 会变成 `@perrylink/dsh-github`），问题只在表里那一行的内容。

3. **`plugin.json` 没有任何宿主通道**：该包带 `plugin.json`（`{ name: "hindsight-coding-agents", version: "0.8.5", description: "Long-term project memory for coding agents", … }`），但全仓 grep `plugin.json` 在宿主侧零引用。它只有插件自己能读——见 §1.5 的可选阶段 A3。

4. `description` 来源是 `manifest` 层（`metaOf` 返回空 → `packageOf().manifest.description`）。所以描述是那段 122 B 的英文长句，被 `summarize(text, 120)` 截到 120 码点再补 `…`：

```
Reflect-only Hindsight long-term memory for coding agents (harness-pluggable: opencode, …), with automatic background…
```

### 1.5 修法

三个子阶段，前两个必做，第三个可选。

> **A1 / A2 / A3 三阶段全部作废**，由
> [`方案-原始名完整描述与家族自动发现.md`](方案-原始名完整描述与家族自动发现.md) §1 取代。
> 原因是 A1 的前提不成立：把宿主 `locale` 标题提到表前面，保住的是「意译优于直译」，而真正的问题
> 恰恰是那张表把品牌写成了能力词（`hindsight` → 记忆、`free_search` → 搜索、`image_gen` → 图像）。
>
> 0.8.0 改为**删掉整张表**：label 一律由包名派生（`rawLabelOf(pkg)`），**宿主 `locale` 的 `title`
> 也不再读**——那正是「记忆」的第三个来路。网关名同时回归 family id（`session_query` 不再缩成
> `session`）。想保留 `GitHub` 这类品牌大小写，用 `families.github.label` 覆盖。
>
> 本文件其余部分仍然有效并已落地：§2 的空网关修法（`callableNames(scope)` 取代 `knownNames()`）、
> §2.6 的撤回解冻、§2.7 的 `no-tools` 原因。下面保留原文仅为记录当时的分诊过程。

（以下为原文，未改动。）

#### 阶段 A1（卫生）：取值链反转

`lib/family-labels.js:116` 改为：

```js
const label = meta?.title ?? byPackage?.label ?? byId?.label ?? humanizeLabel(id);
```

规则表述从「本表短名 → 宿主标题 → 驼峰化」变成「**宿主可用的本地化标题 → 本表 → 驼峰化**」。理由：宿主标题是插件作者写的、带 locale 的权威名字；表只能是兜底。配置里的 `families.<id>.label` 仍然最高（由 `lib/discovery.js:268` 施加）。

**实测：这一改动今天不改变任何一行。** 逐行核对 13 个家族：

| 家族 | 现在 | A1 之后 | 为什么不变 |
|---|---|---|---|
| `fs` | 文件读写工具 | 文件读写工具 | 宿主 locale title 本就胜出（表无行） |
| `fs_search` | 文件搜索工具 | 文件搜索工具 | 同上 |
| `github` / `blender_plugin` / `image_gen` / `mcp_connector` / `video_storyboard` / `free_search` / `schedule` / `session_query` / `hindsight_coding_agents` | 表里的短名 | 表里的短名 | 这些包无 `locale/`，宿主标题 = 包名 → 被丢弃（`lib/plugin-meta.js:232-234`） |
| `tavily` / `computer_use_win` | Tavily / Computer Use Win | 同左 | 表无行，宿主标题 = 包名被丢弃 → 驼峰化 |

所以 A1 是纯粹的防回归改动：它保证「将来某个第一方包补上 locale 后，表不会把它盖掉」。同步要改的注释与断言：`lib/family-labels.js:93-112` 的层序说明、`test/run.mjs:117-126` 的注释（现为 "the host's localized title is used when the table has none"）与新增一条「宿主标题胜过表」的用例。

#### 阶段 A2（必做）：表按语义分栏，hindsight → `Hindsight`

```js
"@vectorize-io/hindsight-coding-agents": {
  label: "Hindsight",                                       // 品牌名，不译
  description: "Repository memory: knowledge pages, capture, recall",
  gateway: "hindsight",
},
```

并在文件头把规则写死，避免下一个人再犯：

```
 * 表的 label 只写「宿主说不出名字时该显示什么」：
 *   · 品牌/产品名 → 保留原名，不翻译（Blender、GitHub、Tavily、Hindsight）
 *   · 通用能力 → 中文短名（搜索、图像、视频、日程、会话检索、MCP 管理）
 * 判断标准：这个名字属于某个产品或公司，还是描述一类动作。
```

副作用（全部实测，见 §6）：网关描述 `网关 · 记忆：…` 141 B → `网关 · Hindsight：…` 144 B；notice 名单 238 B → 241 B。合计 **+6 B**。

#### 阶段 A3（可选）：把 `plugin.json` 当作描述的第 4 层

`lib/plugin-meta.js` 的 `readAt()` 已有三级（`metaOf` → `manifest.description` → 表的 hint）。若再加一级「包内 `plugin.json` 的 `description`」，hindsight 的描述会变成：

```
网关 · Hindsight：Long-term project memory for coding agents
```

141 B → 64 B，**单家族 −77 B**，而且是插件作者自己写给 harness 读的一句，比 `package.json` 里那句带 "(harness-pluggable: opencode, …)" 的营销长句更贴切。

但它是**私有通道**：宿主不读 `plugin.json`，只有本插件读，等于自造第二套元数据规则。建议做成默认关闭（或只在 `package.json` 描述含未闭合括号 / 超过 N 字符时才试），并在 README 说明来源优先级。收益 77 B 不值得引入一条私有约定——**列为可选，不建议在本版做**。

### 1.6 验收（问题 A）

## 2. 问题 B：wire 上的空网关「网关 · 文件搜索工具」

### 2.1 现场

```
$ curl -s http://127.0.0.1:<GUI 端口>/api/dsh-tool-gate/describe | jq '.value.families[] | select(.id=="fs_search")'
{ "id": "fs_search", "label": "文件搜索工具", "count": 0, "hidden": true,
  "packages": ["@deepseek-ai/dsh-tool-fs-search"],
  "promptDisclosure": { "available": true, "reason": "ready", "chars": 0, "names": ["tool:glob", "tool:grep"] } }
```

同一时刻 wire（`cordis_inspect_query` → `host/Tool.listTools`：列出**全部**注册名，含每个 scope 的层、网关、内置工具；`describe` 报的 `wireToolCount` 只是主会话冻结面上的工具数，两者不等价，后者会随会话的常驻工具变化）里：

- **有** `fs_search` 网关，description = `网关 · 文件搜索工具：让 AI 按文件名或文本内容搜索本地文件。`，参数 schema 与其它网关同形（`action` enum `list`/`call` + `tool` + `arguments`，400 B）；
- **没有** `fs` 网关（家族 `enabled:false`），但它的成员 `write` / `edit` / `read_image` 都在 wire 上（`lib/families.js:218-221`：`enabled === false` 的家族成员一律保留）；
- **没有** `glob` / `grep`（wire 上只有 `ops_glob` / `ops_grep`，来自 dsh-ops）。

即：这个网关的 `action: "list"` 只能回「没有成员」，`action: "call"` 无成员可调——纯占位，而且它的 86 B 描述 + 400 B schema 每轮都在付。

### 2.2 三个名字集合

同一个「家族有没有成员」的问题，代码里有三个不同答案来源：

| 集合 | 定义 | 代码位置 | 含被 restriction 屏蔽的名字？ | 含 agent 层注册的名字？ |
|---|---|---|---|---|
| ① `knownNames()` | global 的 `view().knownNames` ∪ 每个 agent 的 `view().knownNames` | `lib/index.js:194-218` | **含** | 含 |
| ② `schemas(agent)` | 该 agent 的 `view().visible` → schemaOf | 宿主 `dsh-tools/lib/index.js:3119-3121`；插件经 `registrySchemas` `lib/index.js:311-321` | 不含 | 含（own 层无条件 visible） |
| ③ `view(scope).visible` | 继承层过 `layers.every(l => l.admits(name))`，外加 own 层全部 | 宿主 `dsh-tools/lib/index.js:3055-3081` | 不含 | 含 |

- 注册网关用的是 ①（`emptyFamilyIds()`，`lib/index.js:528-543`）→ 判定 `fs_search` 非空 → 注册；
- 页面 `hidden`（`lib/bridge.js:167` `hidden: members.length === 0`）、`membersOf`（`lib/dispatch.js:48-64`）、`membersByFamily`（`lib/index.js:362-378`）用的是 ②→ 0 成员。

**两套集合判定同一件事，结果必然可能不一致。** 这就是空网关。

### 2.3 为什么 ① 会包含 `glob`/`grep`——两个原因叠加

这一点必须说清楚，否则会以为「换成 `visible` 就好了」：

1. **`knownNames` 按宿主定义不受 restriction 过滤。** 宿主 `view()` 的实现（`dsh-tools/lib/index.js:3055-3081`）：

```js
const visible = new Map(); const knownNames = new Set(); const restrictableNames = new Set();
for (const [name, definition] of inherited) {
  knownNames.add(name); restrictableNames.add(name);
  if (layers.every((layer) => layer.admits(name))) visible.set(name, definition);
}
if (own !== undefined) for (const [name, definition] of own.tools.entries()) { knownNames.add(name); visible.set(name, definition); }
```

`knownNames.add(name)` 在 `admits()` 之前，无条件执行——deny 名单里的名字照样算「知道」。

2. **`knownNames()` 的第一次收集是 scope-less 的**（`lib/index.js:211` `collect(undefined)`），而 dsh-ops 的 restriction 落在 **agent 层**：

```js
// dsh-ops/lib/modes/replacements.js
agent.ctx.tools.restrict({ deny });   // deny = ['read','glob','grep'] 经 NATIVE_REPLACEMENTS 映射
```

`restrict()` 经 `layers.effect` 落到该 scope 的 own layer（`dsh-scope` 的 `ScopedLayers.effect`，`@deepseek-ai/dsh-scope/lib/index.js:170-200`）。**全局层没有任何 restriction**，所以 `view(undefined)`（scope-less）的 `visible` 里 `glob`/`grep` 依然可见。

因此：只把 `knownNames` 换成 `visible` 而保留 `collect(undefined)`，**结果不变**——空网关照样被注册。必须同时**排除 scope-less 视图**（当存在 agent 时）。

### 2.4 为什么当年选了 `knownNames()`（不能简单回收）

`lib/index.js:521-526` 的注释写得很明确：

```
 * Emptiness is judged against `knownNames()` — the same set the families were
 * derived from — and not against one agent's view. A scope-less registry read
 * cannot see tools registered inside an agent's `ctx.inject` (the schedule
 * bundle does exactly that), so judging by that alone would call a populated
 * family empty and withdraw its gateway while its tools are collapsed out of
 * the wire, making them unreachable.
```

这个担心是真实的（`dsh-tool-schedule` 确实在 agent 的 `ctx.inject` 里注册），但它选错了修法：正确的答案是「并集」而不是「并集里塞进 scope-less 视图」。宿主语义恰好保证了并集的可行性——**own 层注册的工具无条件进 `visible`**，所以 agent 层注册的 schedule 工具在 agent 的 `visible` 里一定存在，不需要借 scope-less 视图来找。

### 2.5 修法：一个判定函数，两个消费者

```js
/**
 * Names that at least one session scope can actually call.
 *
 * Union of every agent's `visible`, plus the assembling agent itself. The
 * scope-less view is deliberately NOT included once an agent exists: it carries
 * no restrictions, so it reports tools every session has already denied.
 */
const callableNames = (primaryScope) => {
  const names = new Set();
  const scopes = [];
  if (primaryScope !== undefined && primaryScope !== null) scopes.push(primaryScope);
  try {
    for (const agent of ctx.get("agents")?.list?.() ?? []) scopes.push(agent);
  } catch { /* agents service not reachable yet */ }
  for (const scope of scopes) {
    try {
      const view = ctx.tools?.view?.(scope);
      if (view?.visible !== undefined) { for (const name of view.visible.keys()) names.add(name); continue; }
      for (const schema of ctx.tools?.schemas?.(scope) ?? []) if (typeof schema?.name === "string") names.add(schema.name);
    } catch { /* scope not resolvable; skip */ }
  }
  if (names.size === 0) {
    // No agent yet (first assembly) or a host without `view()`: fall back to the
    // unrestricted projection, which is what the old code used unconditionally.
    try {
      const view = ctx.tools?.view?.();
      if (view?.visible !== undefined) for (const name of view.visible.keys()) names.add(name);
    } catch { /* ignore */ }
  }
  return names;
};
```

`emptyFamilyIds(primaryScope)` 改为基于它（`knownNames()` 保留给归属推导 `resolveNow`/`ownerIndex`，那里要的正是「注册过的全部名字」，语义不同，不能复用）。

`handleAssemble` 里 `syncGateways` 已经拿得到 `context.scope`，传入即可：

```js
const handleAssemble = async (assembly, context, next) => {
  const live = refreshFamilies();
  syncGateways(live.enabled === true, context?.scope);   // ← 传组装中的 agent
```

**为什么必须传 `context.scope`，而不是只靠 `agents.list()`**：第一次组装时 agent 可能还没进 `agents.list()`，此时并集为空 → 退化到 scope-less 视图 → `glob`/`grep` 又回来 → 注册 → 冻结面里留下它 → 第二轮再撤回（还要付一次解冻，§2.6）。传了 `context.scope`，第一轮就是对的：那条 scope 的 `visible` 已经准确排除了 deny 名单。

`known.size === 0` 的防抖保留（`lib/index.js:532-535`），语义从「注册表还没读出来」变成「没有任何 scope 能读出来」。

#### 与 §2.6 的关系

改完之后，`fs_search` 在**第一次组装时就不会被注册**，不会进冻结面，也就不需要解冻。解冻只是兜底。

### 2.6 撤回网关时必须解冻（frozen 是粘性的）

`lib/state.js:84-91` 的 `adopt()` 把冻结面记成「本会话最终工具集」，`lib/index.js:672` 只在 `frozen === undefined` 时重建。如果网关在**已冻结之后**被撤回，`frozen` 里仍然留着那个 schema，模型会去调一个已经不存在的工具（execute 直接失败）。`lib/index.js:660-667` 已经为「注册失败」写了同样的处理：

```js
if (stillMissing.length > 0) {
  logger?.debug?.(`dsh-tool-gate: gateway(s) not resolvable yet: ${stillMissing.join(", ")}`);
  states.ensure(agent).frozen = undefined;
  return result;
}
```

修法：`syncGateways` 记录上一次的网关名集合，当**有名字消失**时，清掉所有 state 的 `frozen`：

```js
const disappeared = previous.filter((name) => !gatewayNames.includes(name));
if (disappeared.length > 0) {
  for (const state of states) state.frozen = undefined;   // 下一次组装重建，代价是一次前缀重写
  logger?.debug?.(`dsh-tool-gate: withdraw ${disappeared.join(", ")}, unfreezing to drop dead entries`);
}
```

代价与取舍要写进文档：每次解冻都会**重写一次提示词前缀**（正是 `freeze` 想避免的），所以解冻只在「网关消失」时发生，且只在缺陷修复的那一刻发生一次，之后重新冻结。不要为了少一次重写而留住一个死工具。

### 2.7 附带：0 成员家族的 `promptDisclosure.available`

`fs_search` 的 `promptDisclosure` 报 `available: true, reason: "ready"`，但它的成员一个都不在 wire 上——这个开关永远不会有内容可披露。成因：`lib/bridge.js:112` 的 `available` 只看 `row.disclosureAvailable`，而后者在 `lib/prompt-scan.js:496` 只判断「家族是否收起、是否 required/immutable」，**不看成员是否存在**。

影响范围要说清楚：**页面不可见**。`lib/client.js:423` 用 `.filter((family) => family.hidden !== true)` 渲染家族行，`fs_search` 是 `hidden: true`，那一行连同它的开关都不会画出来。所以这是 API 层的不一致，不是用户可见缺陷。

建议顺手改（低成本）：`disclosureFor(family)` 在 `members.length === 0` 时返回 `{ available: false, reason: "no-tools", … }`。代价是要同步三处枚举：`lib/prompt-scan.js:77-85` 的 `REASON_PRIORITY`、`lib/client.js:350-357` 的 `promptNote`、`test/e2e.mjs:1060-1076` 的合法值列表。若想零风险，也可以先只改文档不改代码——B 的可见症状不在这里。

### 2.8 两件不是 bug 的事（免得顺手误改）

1. **`fs` 家族 `enabled: false` 而成员仍在 wire**：`lib/families.js:218-221` 明确「定义不存在或 `enabled === false` → 保留在 wire 上」。关闭家族 = 不折叠，不是删除工具。正确。
2. **`fs_search` 的 `reason: "ready"`**：`reasonFor`（`lib/prompt-scan.js:442-451`）回答的是「如果有内容，这个开关能不能用」，不回答「有没有内容」。文案语义正确，问题在 `available` 没结合成员数（§2.7）。

## 3. 不变量与风险

### 3.1 必须守住的不变量

1. **agent 层注册的工具必须仍能折叠**：`dsh-tool-schedule` 在 `ctx.inject` 里注册，它的网关必须继续存在。并集方案依赖宿主「own 层无条件 visible」的语义，已逐行核对（`dsh-tools/lib/index.js:3072`）。
2. **`families.<id>.enabled === false` 的家族不注册网关**（`lib/gateways.js:191`），与判空无关，不能被新逻辑覆盖。
3. **没有 agent 作用域时的行为不能更差**：`agents.list()` 为空、或宿主没有 `view()`（现有两套测试的假宿主都是如此）时，退化为 `schemas(scope)` 且保留 scope-less 兜底——与今天等价。
4. **配置覆盖仍然最高**：`families.<id>.label` / `description` 由 `lib/discovery.js:268-271` 施加，`descriptionSource = "override"`。
5. **网关名（wire 名）永远由家族 id 推导**，不跟随 label（`lib/index.js:175-176`）——改名不能动 wire 面。
6. **冻结面不会被无谓重建**：只有网关消失才解冻（§2.6）。

### 3.2 风险

| 风险 | 触发条件 | 影响 | 处置 |
|---|---|---|---|
| 并集漏掉某个只对子代理可见的家族 | 家族工具只在子代理 scope 注册 | 网关被撤回、成员又已折叠 → 不可达 | 并集包含**所有** agent（不只主会话）；`known.size === 0` 时抑制全部；单测覆盖「只在子代理里注册」 |
| 第一轮组装误判 | `agents.list()` 尚未包含当前 agent | 注册后又被撤回 | `handleAssemble` 传 `context.scope`（§2.5） |
| 解冻导致前缀重写 | 网关集合收缩 | 一次 prompt 前缀重算，缓存失效一轮 | 仅网关消失时触发；日志可查 |
| A1 反转改变某些行的 label | 某个包将来补 `locale/` | 表里的中文短名让位给宿主标题（预期行为） | 用 `families.<id>.label` 可显式覆盖 |
| `记忆` → `Hindsight` 影响文档与截图 | README、docs 多处 | 数字/文案不一致 | §4 文档同步清单 |

### 3.3 回滚

两个问题互相独立，都可单点回滚：

- A：`git revert` 只含 `lib/family-labels.js` 的 hunk；
- B：`emptyFamilyIds` 换回 `knownNames()` + 删掉解冻逻辑（一个函数体的改动）。

没有配置项开关：这两个都是缺陷修复，不引入新的 `config` 字段（避免「配置能修 bug」的错觉）。
